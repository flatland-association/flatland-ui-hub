# Graph env playground: step a GraphRailEnv on a real network

Status: built, 2026-10-26 (see "Deviations while building"); how to run it: `docs/reference/graph-env-playground.md`. Branch `feature/graph`,
cut from `main` at 2f4dbcb. The PR targets `main`, not `explore_db`, as decided
for this prototype.

## Goal

A single page at a hard-coded URL, `/graph-env`. It shows the Walenstadt rail
network on an OpenStreetMap basemap and one train that steps along it with the
shortest-path policy, as at the end of the notebook in
flatland-scenarios #36. Reloading the page creates a new env.

No integration with the rest of the app: no `SessionStore`, no interaction
modes, no tours.

## Backend

### 1. Data: precompute once, commit the result

`backend/scripts/build_graph_env_network.py` is an offline script. Its
requirements are listed in its header: osmnx, plus a checkout of
flatland-scenarios at `c2bc7b4093`, given as an argument and not vendored.
It does the following:

1. `load_track_graph("walensee.graphml")`, then `build_double_vertex_graph`,
   then `add_actions`, exactly as `create_env` does.
2. It writes `backend/app/graph_env/data/walensee.json`: networkx node-link
   data of the double vertex graph.
   - **Nodes:** `x`, `y`, `prohibited_actions` (ints), and an `is_switch` flag.
     The flag drives the node styling, as the notebook's categories do.
   - **Edges:** `length` (float metres), `actions` (ints), and `geometry` as a
     `[[lat, lon], …]` list oriented **from u to v**.

   Orienting the geometry is the only real-geometry work.
   `build_double_vertex_graph` copies each OSM edge's data, geometry included,
   onto both directed vertex edges. The geometry follows the OSM drawing
   direction, so the script reverses it where its first point is not at u.
   An edge without geometry becomes the straight line `[u, v]`.

`walensee.graphml` is copied from the scenarios branch into
`backend/app/graph_env/data/`, next to the JSON, as the source of truth. The
JSON is regenerated by hand when the graphml changes.

### 2. Env construction and policy: `backend/app/graph_env/`

- `network.py` loads the JSON into an `nx.DiGraph`. It turns `actions` and
  `prohibited_actions` back into `set[RailEnvActions]`.
- `env_factory.py` is copied from `double_vertex_graph_to_env.py` with a
  header naming the source and the commit:
  - `resource_map`, `rational_lengths` and `create_env` are copied with the
    `add_actions` call removed, because the actions are precomputed.
  - `GraphShortestPathPolicy` is copied verbatim.
  - It adds the notebook's step-through scaling: divide the lengths by the
    shortest edge, then `rational_lengths`. The constants `SOURCE`, `TARGET`,
    `SPEED`, `LATEST_ARRIVAL` and `MAX_EPISODE_STEPS` are hard-coded here.
- `service.py` holds `GraphEnvSession(id, env, policy, lock)`:
  - `reset()` builds the env and a new policy and calls `env.reset()`.
  - `step(n)` loops `actions = policy.act_many(handles, [env] * len(handles))`
    and `env.step(actions)` until done or n steps.

  **Live env, not a precomputed trajectory.** Each step advances the
  session's live `GraphRailEnv`, and positions are read from `env.agents`
  afterwards. The notebook's map step-through works the same way: cell 90
  wraps a fresh env in `PolicyRunner(by_pass_env=…)`, calls
  `step_runner.step()` once per click, and reads `step_env.agents`.

  - The full run up front (cell 88, `run_shortest_path_policy`) only prints
    `trains_positions` and checks that the train arrives. It is not used here.
  - Precomputing would work for one train with a deterministic policy, but
    the future extensions need a live env: policy changes, malfunctions, and
    interventions or what-ifs in the middle of an episode.
  - The cost is one HTTP round trip per step while playing. That is fine up
    to the toolbar's 10 steps/s.

  It does not use `PolicyRunner` or `Trajectory` either: they need a data
  dir, and reading graph trajectories back is broken upstream.

  The sessions live in an in-memory dict capped at 20 entries; the least
  recently used is evicted first. The cap prevents leaks because every reload creates a
  session.
- `projection.py` turns the env state into its JSON form:
  - `fraction = speed_counter.distance / speed_counter.edge_length`, as in the
    notebook's `train_location`.
  - It interpolates along the oriented geometry by `fraction` of its length,
    measured with the haversine formula over the polyline.
  - The bearing is that of the current geometry segment, so the train icon
    turns with the track and not with the straight line from u to v.
  - `remaining_path` is a list of polylines, **one per edge**, so the
    frontend can draw it segment by segment like the grid does. The first one
    is the rest of the current edge, from the train's interpolated position to
    v. The rest are the policy's planned edges (`GraphShortestPathPolicy.
    _shortest_paths[handle]`, as the notebook's `show()` uses them), each
    with its oriented geometry. The list is empty once the train is `DONE`.
    This is the graph equivalent of the grid's forecast cut at the current
    step.
  - `target` is the `[lat, lon]` of the agent's target vertex
    (`agent.waypoints[-1][0]`), for the target marker.

### 3. API: `backend/app/api/graph_env.py`

It is mounted with `prefix="/graph-env-api"` in `main.py` (see the deviations). That `include_router`
line is the only change to existing backend files, apart from requirements.

| Method | Path | Returns |
|---|---|---|
| `GET` | `/graph-env-api/network` | Tracks: one polyline per track pair (plain and `_prime` twins drawn once, as in the notebook's `create_map`). Nodes with `is_switch`. Bounds. Static, cacheable. |
| `POST` | `/graph-env-api/sessions` | `{id, state}`. Creates and resets an env. The page calls this on load. |
| `POST` | `/graph-env-api/sessions/{id}/step?n=1` | `state`. Returns 404 for an unknown id. |

`state` has this shape:

```
{step, max_episode_steps, done,
 agents: [{handle, state, edge: [u, v] | null, fraction,
           lat, lon, bearing,
           remaining_path: [[[lat, lon], …], …],   // one polyline per edge
           target: [lat, lon]}]}
```

The route and the target are part of `state`, so **there is no second API**.
The grid gets its route from a separate forecast (`scenarios[].trajectories`),
because there it is a simulated look-ahead. Here the policy's plan is already
in memory after each step, so sending it with the step is cheaper than a
second request. A separate forecast endpoint only becomes necessary when
other policies need a simulated look-ahead (see the future extensions).

## Frontend

### 6. Page

The page is `features/graph-env-playground/`, shown by a `showGraphEnv` getter
for `/graph-env` in `app.component.ts` and `.html`. It uses the same pattern as
`/infrastructure-builder` and `/scenarios`. The layout is the toolbar on top,
the map on the left and the event feed on the right.

### 7. Map: new, because nothing geographic exists to copy

`graph-env-map.component.ts` uses Leaflet: it adds `leaflet` and
`@types/leaflet` to npm. `leaflet/dist/leaflet.css` goes into the `styles` in
`angular.json`. Stylelint only lints `src/**/*.scss`, so Leaflet's own
colours stay out of the gate.

- **Basemap:** `tile.openstreetmap.org` with the required attribution.
- **Tracks and nodes:** vector layers with a `className` and no `color`
  option. They are styled in SCSS with tokens, so no literal colours appear in
  the TS either. Switches get a different node class, following the notebook's
  categories.
- **Remaining route (decision 12), in the grid's style** (see "How the grid
  map shows a train's route" below):
  - **When it shows:** for the hovered train and the selected train, the
    grid's `visibleTrajectoryHandles` without the notification and option
    hovers. Hovering the train marker shows it. Clicking the marker toggles
    the selection, which keeps it shown. Clicking the empty map clears the
    selection. `GraphEnvStore` holds `selectedHandle` and `hoveredHandle`.
  - **How it looks:** one Leaflet polyline triple per edge in
    `remaining_path`: casing, solid line and flow line. They use the grid's
    classes and SCSS unchanged (`trajectory-future-segment-casing`,
    `trajectory-future-segment`, `trajectory-future-segment-flow`, copied
    from `flatland-map.component.scss`), so the animated dash looks the same.
    The layers sit above the tracks and below the train.
  - **Colour:** as in `_trajectoryColorForHandle`: `--app-select-color` for
    the selected train, otherwise `AgentColorService.getColorSolid(handle)`.
    It is set on the path's `stroke`, as the grid's `[attr.stroke]` does, so
    no literal colours are added.
  - **No layer toggle:** there is no layer panel on this page, so the route
    behaves as if `agentTrajectory` were on.
- **Target marker (decision 12):** on hover or selection, as in
  `isAgentTargetHighlighted`. It is a `divIcon` at `state.agents[].target`
  holding the grid's `agent-target-highlight` SVG: ring, dot and cross. The
  markup, the classes, `--agent-target-color` and the `selected-target`
  variant are copied unchanged from the grid.
- **Train (decision 11):** a `divIcon` holding the grid map's train glyph, the
  `flatland-agent-marker` SVG in `flatland-map.component.html`. Its markup and
  classes are copied unchanged, and it uses the agent colour from
  `AgentColorService`. The notebook's locomotive PNG is not used. The glyph
  is a circle with the train number and has no direction, so it is not
  rotated (see the deviations); `bearing` stays in the API.
- **Viewport:** fit to bounds once on load. After that, the view is never
  changed in code, so zoom and pan are kept, as in the notebook.
- **Motion:** while playing, the marker is tweened linearly from the previous
  to the new position over the step interval with `requestAnimationFrame`. When
  paused, it snaps to the exact state, following the rule in
  `smooth-playback.md`.

### How the grid map shows a train's route (for comparison)

The grid map never shows a plain "shortest path". It shows, on demand, the
**forecast trajectory under the active policy**. With a shortest-path policy
the two coincide.

- **Route:** `selectedTrajectoryFutureSegments` (`flatland-map.component.ts:633`)
  draws the train's future segments.
  - The source is the forecast of the active, or previewed, scenario:
    `store.scenarios()[…].trajectories[handle]`, cut at the current step.
  - It is drawn exactly per segment, so only the driven branch of a switch is
    marked. Each segment is drawn three times: a casing, a solid line and an
    animated dashed "flow" line.
- **When it shows** (`visibleTrajectoryHandles`, `:540`): only while the
  `agentTrajectory` layer is on. The layer is on by default but off in
  Director (`core/layout/layer-mode-defaults.ts`). It then shows for:
  - the **selected** train
  - the train **hovered** on the map
  - trains hovered in a notification or another panel
    (`store.notificationHoverHandles`)
  - every train an option moves while that option is previewed
- **Colour:** the agent colour (`AgentColorService.getColorSolid`), or
  `--app-select-color` for the selected train.
- **Target:** on hover or selection (`isAgentTargetHighlighted`, `:2131`) the
  target cell gets a ring, a dot and a cross (`.agent-target-highlight`) in the
  agent or selection colour.
- **Past path:** `selectedTrajectoryPastPath` (`:593`) is computed but not
  rendered in the template.
- **Planned routes for all trains:** the separate `allPlannedRoutes` layer
  draws them dashed, and is off by default.

The prototype follows this for the route and the target. It leaves out
the parts that need the rest of the app: the layer toggle, notification and
option hovers, and planned routes for all trains. The past path isn't drawn
in the grid either.

## Implementation steps, one commit each

Every commit does one kind of change, so each diff can be read on its own.
The PR is reviewed commit by commit.

**Copied code: copy first, adapt after.** Copied code always lands in two
commits:

1. a **verbatim copy** of the upstream or original file, with only a header
   comment naming the source path and commit added. The reviewer can check it
   with `diff` against the source.
2. the **adaptation**, a normal diff showing exactly what changed.

This applies to the scenarios code, the toolbar and the event feed. The diff
in the second commit is also what a later merge of the two setups has to undo.

The backend can be reviewed and tried (`curl`) before any frontend commit.
Each commit leaves the build working: `ng build` passes, and the new tests
pass. Existing backend tests may stay red from commit 2 on (decision 10).

## Risks

- **flatland-rl #542 is pre-5.0 and breaking** for speed and distance
  internals and for the graph type names. The grid backend is not adapted (1a),
  so existing tests may fail on this branch. The PR is opened as a **draft**
  and red checks are accepted (decision 10). Building step 1 runs the full
  `pytest` once and records the failures in the PR description; they are not
  fixed or skipped there.
  #542 also differs from the `flatland-43-upgrade.md` work on `explore_db`.
- **OSM tile usage policy:** fine for development and demos with attribution,
  but not for heavy use. See the self-hosted tiles extension.
- **The copies drift from their originals.** The header comments and the
  minimal diff keep a later merge cheap.

None. Preselecting the train on load was decided against, to match the grid:

## Future extensions

Compiled from the review discussion:

- **Editable scenario:** source, target and speed per train, chosen on the
  map. The grid app can't do this either (see the Decisions section).
- **Several trains and a generated timetable,** "Remaining" in
  flatland-scenarios #36.
- **Policy selection:** enable the toolbar's policy dropdown (other graph
  policies, or a CBS/PP solver from `flatland-blackbox`).
- **Event feed contents:** departed, arrived, at a switch, and malfunction
  events, then triage, as in the grid feed.
- **Malfunctions** (`malfunction_generator`).
- **Merge with the grid setup in one view:** fold the toolbar and event-feed
  copies back into the originals behind a shared store interface, then
  `SessionStore` and interaction modes.
- **Recording and replay** of trajectories and env persistence. Both are
  blocked upstream: graph trajectories can't be read back, and `GraphRailEnv`
  can't be saved yet ("Remaining" in scenarios #36).
- **Session lifecycle:** TTL, explicit delete, or persistence instead of the
  in-memory cap.
- **Self-hosted or offline tiles,** or a tile-less view for kiosk and demo use.
- **Other networks,** e.g. `sargans_reversing_loop.graphml`, and a network
  picker.
- **Generate the network JSON in the scenarios pipeline** (or CI) instead of
  the one-off script, once that code is a package.
- **Move to flatland-rl `main`, then a release,** once #542 is merged and
  released. Then reconcile with the 4.3 code on `explore_db`.
- **Progress on long edges,** like `RenderTool`'s `show_agent_progress`.
- **The rest of the grid's route display:** the `agentTrajectory` layer
  toggle, hover from the event feed (`notificationHoverHandles`), and
  planned routes for all trains (`allPlannedRoutes`).
- **Show the forecast, not only the shortest path,** once other policies are
  selectable, as the grid does through `scenarios[].trajectories`.
- **German and French translations** for the new keys.
- **Smoother motion** through the grid's `SmoothMotionService` and
  `StepCadence`, instead of the local tween.
- **Direction cue on the train glyph,** from the `bearing` the API already
  sends (the grid glyph has none either).
- **Dark basemap** in the dark scheme: the OSM tiles stay light, which is why
  the graph tokens are fixed rather than `light-dark()`.
