# Gotthard — a real-network showcase built from public data

> **Status:** draft, 2026-10-04. Nothing built yet. Data availability for the
> network checked; the timetable (GTFS) not yet downloaded.
> **Why:** the Gotthard axis has a built-in dispatching decision that fits all
> three interaction modes: the base tunnel (GBT) or the 1882 mountain line, and
> a real closure case (GBT derailment, Aug 2023). Olten is a hub and PF–CH is a
> hand-built corridor; this is a long axis with a genuine route choice.
> **Companions:** [scenario-infrastructure-gallery.md](scenario-infrastructure-gallery.md)
> (network / traffic / disruption layers) · [data-provenance.md](../reference/data-provenance.md)
> · `backend/app/fixtures/olten/SOURCE.md` (precedent for a sourced fixture).

## 1. What we build

A **Network** (topology), a **Traffic** (timetable) and one or two
**Scenarios** (disruptions), registered as one preset in
`backend/app/core/scenario_presets.py`, so the `/scenarios` gallery lists it
without frontend changes (P1 boundary of the gallery plan).

Generated by a script, not drawn by hand, so it can be re-run and extended:
`backend/scripts/generate_gotthard.py` → `backend/app/fixtures/gotthard/`.

## 2. Network — what the public data gives us

Checked 2026-10-04 against the SBB open-data set
[`linie-mit-betriebspunkten`](https://data.sbb.ch/explore/dataset/linie-mit-betriebspunkten/)
(operating points with line number, km and lat/lon; API reachable without a key):

| Part | Line in the dataset | Operating points |
|---|---|---|
| Mountain line | 600 *Immensee – Bellinzona – Chiasso* | Arth-Goldau, Erstfeld, Amsteg-Silenen, Gurtnellen, Wassen, Göschenen, Airolo, Faido, Biasca, Bellinzona, Lugano, Chiasso, plus the passing loops (`Spw`) |
| Base tunnel, west tube | 594 *GBT West* | Rynacht (Abzw), Sedrun SMF, Faido SMF, Pozzo Negro |
| Base tunnel, east tube | 595 *GBT Ost* | Rynacht (Spw), Sedrun SMF, Faido SMF, Pozzo Negro, Pollegio, Giustizia |
| Uri access | 601, 605 | Rynacht – Erstfeld Nord, Sisikon – Gruonbach |

The two multifunction stations **Sedrun** and **Faido** (`SMF`) are the
crossovers where a train can change tube. That is the physical basis of the
disruption: with one tube closed, trains run single-track between the SMFs.

**Not in the data:** track layout inside stations (switches, loops, platform
count). Passing loops appear as operating points but not their length or
switches. Stations are therefore modelled as a fixed pattern (two main tracks
plus loops where the dataset lists a `Spw`/`c bin`), and this is marked as
*derived* in the provenance.

### Cell model (decision needed, see §6)

Proposed: **one cell ≈ one operating-point-to-operating-point section, split
into ~1 km blocks** on open line. Scope for stage 1:

```
Arth-Goldau ─ Erstfeld ─┬─ Basistunnel West/Ost (Sedrun, Faido crossovers) ─┬─ Biasca ─ Bellinzona
                        └─ Bergstrecke (Amsteg, Gurtnellen, Wassen, Göschenen, Airolo, Faido) ─┘
```

Stage 2: Immensee/Zug/Luzern in the north and Lugano/Chiasso in the south.

## 3. Traffic — the timetable

- **Passenger:** the Swiss GTFS timetable
  ([opentransportdata.swiss](https://opentransportdata.swiss/), file
  `timetable-2026-gtfs2020`, ~250 MB, not downloaded yet). Filter to trips that
  pass Erstfeld–Bellinzona, take one representative hour or two. Trips give
  stop sequence and times → earliest departure / latest arrival per train.
- **Freight:** **not in GTFS.** The path catalogue is not public. Freight
  trains are added as *synthetic* traffic (count and slot from public
  statistics, e.g. SBB `zugzahlen`), marked as such in the catalogue
  provenance. Without them the Bergstrecke is nearly empty and the showcase
  loses its point (mixed speeds).
- Speed classes via Flatland speed ratios (freight slower than IC).

## 4. Scenarios

1. **Baseline:** regular timetable, nothing wrong.
2. **GBT closed (one tube):** single-track operation between the SMFs; reroute
   freight and some passenger trains over the Bergstrecke. The decision all three
   modes work on.
3. **GBT closed (both tubes):** everything onto the Bergstrecke, capacity far
   below demand; forces prioritisation (the Director case).

Format: `disturbances/*.json` as for `pf_ch`.

## 5. Steps

1. Generator: SBB API → graph (nodes, km, lat/lon) → `gotthard.scene.json`
   (same schema as `pf_ch`) and `gotthard.geography.json` (names, like Olten).
2. Timetable: download GTFS, filter, map to agents; add synthetic freight.
3. Preset + catalogue metadata + `SOURCE.md` (licence, retrieval date).
4. Disturbances and a plan (`generate_plan.py`) for the baseline.
5. Backend test (loads, runs, no deadlock in baseline) and gallery check.
6. Verify in the running app.

## 6. Open questions

- **Block length / time step:** 1 km per cell? It decides whether run times
  match the timetable and how big the grid gets (~200 columns).
- **Station model:** a fixed pattern is a guess. Is that acceptable for a
  showcase, or do we want to hand-check Erstfeld, Arth-Goldau and Bellinzona?
- **Freight volume:** which counts do we claim, and is "synthetic" in the
  catalogue enough for the thesis?
- **Licence:** SBB open data and the GTFS licence terms must be quoted in
  `SOURCE.md`; to be read before the first commit of data.
- **Scale:** the planners (CBS/PP) with 30+ trains; measured on Olten first.

## 7. Findings 2026-10-04 (GTFS downloaded, network checked)

**Timetable** (`gtfs_fp2026_20260930.zip`, Tuesday 2026-10-06, extracted in a
scratchpad, not committed). 100 through passenger trips Arth-Goldau ↔
Bellinzona/Lugano per day, ~6 per hour: EC 28, IC2 22, IC21 16, PE 2 (all
through the base tunnel, no stop at Erstfeld/Biasca) and IR26 16 + IR46 16
(mountain line, stopping at Erstfeld, Göschenen, Airolo, Faido, Biasca, …).
Passenger traffic alone is thin, so synthetic freight (§3) is not optional.

**Design problem: the two routes have different lengths, Flatland cells do
not.** Rynacht → Giustizia is 96 km on the mountain line (BG) and 65 km through
the base tunnel (GBT). Flatland moves a train one cell per step at a constant
per-train speed, and the two routes must meet at the same columns. So with a
straight two-row layout both routes take the same number of steps, and the
base tunnel's whole time advantage — the reason a closure is a decision —
disappears. A different cell length per route does not help for the same
reason (equal column span = equal steps for the same speed).

Options:

| | Layout | Keeps the time difference | Cost |
|---|---|---|---|
| A | Mountain line drawn as a **U** below the straight tunnel (down ~16 rows, east 65 columns, up) | yes, exact | curves and vertical crossovers/stations; heavier generator and UI schematic, not geographic |
| B | Straight parallel rows, equal columns | **no** | simple; showcase loses its point |
| C | Straight rows, mountain line padded with slow zones (station/loop cells) | roughly | arbitrary, hard to explain |

Recommendation: **A**, shown as a schematic (Netzgrafik-style, not a map).
Decision pending.

### 7a. Does Flatland 4.3 solve it? (checked 2026-10-04, read-only)

Read the 4.3.0 sdist and ran it in a throw-away venv in the scratchpad; the repo
stays on 4.2.6 (4.3 is not ours to integrate, see `flatland-43-upgrade.md`).

- **Yes in principle.** 4.3 has `GraphRailEnv.from_graph(g, resource_map,
  agent_waypoints, agent_speeds, timetable_generator, …)`: a network as a plain
  `networkx` graph with string nodes, no grid. Tested on a diamond with a
  10-node and a 15-node route: the trains arrive after 14 and 19 steps. So a
  96-node mountain line next to a 65-node base tunnel gives the real time
  difference with no layout trick. `resource_map` (node → occupancy unit) is
  the block-section concept, and the timetable generator can carry real
  departures.
- **Not usable for the showcase today.** Everything we run on is grid-based
  (`env.rail`, `agent.position` as (row, col), the scene adapter, tile
  resolver, plans, disturbances by cell, the network view). The graph env has
  string positions. The changelog calls it "graph generalization part 1–6", and
  part 5 is only a partial fix for symmetric switches.
- **`len` in 4.3 is not a travel time.** `DecisionPointGraphEdgeData.len` is the
  number of grid cells collapsed into an edge (analysis); stepping does not read it.

**Consequence:** build the generator in two layers. Layer 1 emits a neutral
topology (stations, blocks with km, speed limits, crossovers) as JSON. Layer 2
turns it into today's grid scene (option A, U-layout) now. When 4.3 and a graph
path land, only layer 2 is replaced, and the Gotthard showcase gets the exact
time difference without the U.
